TMDB Ingestion Pipeline

A PostgreSQL schema and Python ingestion pipeline that pulls nested movie metadata out of The Movie Database API and into a local database that survives being re-run.

Stack
Python · PostgreSQL · psycopg2
Role
Solo personal project
Year
2026
Status
Complete

2026

Context

The TMDB API returns deeply nested JSON — a single movie arrives with its credits, keywords, release dates, companies, and languages bolted on. Exploratory queries want none of that nesting; they want tables they can join.

I needed a dependable local copy of that data as the foundation for the movie analysis work, shaped for SQL from the start rather than flattened out of CSV dumps after the fact.

Approach

Schema first

  • Core entities — movies, people, collections, production_companies — with reference tables for countries, languages, genres, and keywords.
  • Junction tables carry every many-to-many relationship: cast, crew, genres, keywords, companies, countries, languages, release dates.
  • Reference data is seeded by its own script, so joins never depend on API response order.

Two-stage ingestion

  • Movie IDs are collected from two sources — /movie/popular and /discover/movie sorted by revenue — then deduplicated to a set before any detail request.
  • Full details are fetched per movie with append_to_response=credits,keywords,release_dates and written in batches with psycopg2.extras.execute_values.
  • A separate enrichment pass backfills people rows missing biography, birthday, place of birth, and IMDb id.

Built to be re-run

  • ON CONFLICT upserts throughout, so a second run refreshes rows instead of duplicating them.
  • Release dates are deleted and re-inserted per movie, so re-runs can't stack duplicates.
  • Rate limiting is configurable (INGEST_DELAY), and run scope scales with INGEST_PAGES — small for iteration, large for bulk loads.
  • The core movie insert is treated as critical: if it fails, its dependent inserts are skipped so junction tables never hold orphans. Everything non-critical is wrapped so one bad payload doesn't kill the run.

Outcome

  • One command — python -m ingest.ingest — lands genres, movies, people, collections, companies, keywords, cast and crew junctions, and release dates in PostgreSQL.
  • Re-runs upsert rather than duplicate, which makes the pipeline safe to schedule or resume.
  • Batch inserts keep write volume down, and a written data dictionary documents definitions, types, and core schemas for anyone else reading the database.
  • Configuration stays in .env — keys and credentials never touch the code.

Notes & limits

Movie detail fetches happen one movie at a time, so a large INGEST_PAGES run takes hours — fine for a bulk load, awkward for iteration. And TMDB doesn't know a film's marketing spend or word-of-mouth, which sets a ceiling on anything downstream that tries to explain commercial performance.
